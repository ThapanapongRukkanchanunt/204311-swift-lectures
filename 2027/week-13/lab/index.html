W13-Lab

เชื่อม Firebase ผ่าน Service และตรวจสิทธิ์

ก่อนเริ่มต้น

[ลิงก์ Edpuzzle — ผู้สอนเพิ่มภายหลัง]

อ่านสถานะบริการสมมติจาก Firebase จริงผ่าน service boundary ตรวจ remote change และสิทธิ์ที่ปฏิเสธ โดยไม่เปิดให้แอปเขียนข้อมูลสาธารณะ

[ภาพตัวอย่างแอป — ผู้สอนเพิ่มภายหลัง]

  1. ก่อนคาบ เตรียม Google account และ Firebase project ที่คุณมีสิทธิ์จัดการ พร้อม Firestore default database ตรวจ quota/ราคาและนโยบายบัญชีด้วยตนเอง ไม่ต้องเปิดบริการแบบมีค่าใช้จ่ายเพื่อทำตัวอย่างนี้
  2. ใช้ Xcode หรือ Swift Playgrounds กับอินเทอร์เน็ต และ browser ที่แก้ Firebase console ได้ ถ้าคอนโซลบน iPad ใช้ไม่ได้ให้เตรียมค่าผ่าน Mac ก่อนคาบ
  3. ห้ามใส่ข้อมูลส่วนตัวลงเอกสารสาธารณะ ห้ามใช้ service-account key ในแอป และไม่ถ่ายภาพ credentials

เตรียมโปรเจกต์

ดาวน์โหลด catch-up starter Week 13 แล้วแตกไฟล์ สร้างโปรเจกต์ SwiftUI App ใหม่ใน Xcode หรือ App ใหม่ใน Swift Playgrounds เก็บ App entry เดิมไว้ เพิ่มไฟล์ Swift ตาม README และแทนเฉพาะ ContentView.swift ของโปรเจกต์ใหม่ Run ให้ผ่านก่อนแก้ตามภารกิจ ไม่ทับโปรเจกต์เดิม Load fake ต้องได้ Sample status และ Revision 0; ยังไม่นับเป็นหลักฐาน cloud จริง

ภารกิจ

1. กำหนดขอบเขตข้อมูลสาธารณะ 20 นาที

  1. ใน Firebase console ของ project ฝึก เปิด Firestore Rules และใช้ ruleset ด้านล่างแทนกฎเปิดทั้งหมดเฉพาะ project ฝึกที่ไม่มีข้อมูลอื่น ห้ามทับกฎของระบบจริง
  2. Publish rules แล้วสร้าง collection courseStatus เอกสาร demo ใน Data ใส่ message แบบ string เช่น Library desk open และ version แบบ integer เป็น 1
  3. อย่าสร้างข้อมูลส่วนตัวใน path นี้ จด project ID จาก Project settings ซึ่งไม่ใช่ credential
  4. ใช้ Rules simulator ตรวจ unauthenticated read ที่ courseStatus/demo ผ่าน แต่ write และอ่าน path อื่นถูกปฏิเสธ

Firebase console — Firestore Rules ของ project ฝึกใหม่เท่านั้น

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /courseStatus/demo {
      allow read: if true;
      allow write: if false;
    }
  }
}

ตรวจผล / แก้ปัญหา: เปิดอ่านเฉพาะเอกสารสมมติที่ตั้งใจ public หาก write ผ่าน ให้ตรวจว่ามีกฎ allow all อื่นอยู่หรือไม่

เก็บภาพที่ 1: ผล Rules simulator ที่ปฏิเสธ write โดยไม่เห็น credentials

2. อ่านข้อมูล cloud จริง 20 นาที

  1. ในแอปกรอก project ID แล้วกด Load live demo
  2. ตรวจ message และ revision ว่ามาจากเอกสาร ไม่ใช่ Sample status ของ fake
  3. อ่าน StatusService.swift หาจุดตรวจ HTTP และแปลง Firestore fields เป็น CloudStatus
  4. เพิ่ม Text("Public synthetic service status") ในหน้าจอเพื่อบอกขอบเขตข้อมูล

ตรวจผล / แก้ปัญหา: เห็น Live accepted และ Revision 1 หากไม่ผ่าน ตรวจชื่อ database/path ชนิด field rules และ project ID ไม่แก้โดยเปิด write ทั้งฐานข้อมูล

เก็บภาพที่ 2: แอปที่แสดง message จาก cloud และ Live accepted

3. พิสูจน์ remote change และ stale state 20 นาที

  1. ใน console เปลี่ยน message เป็น Library desk closed และ version เป็น 2 โดยใช้สิทธิ์เจ้าของ project
  2. กด Load live demo ใหม่ในแอป ค่าต้องเปลี่ยนตามข้อมูล cloud โดยไม่แก้ Swift
  3. กด Test denied path แอปต้องแจ้ง failed และยังแสดงข้อมูลก่อนหน้าพร้อมคำเตือน stale
  4. ปรับข้อความ feedback ให้ชัดว่าเป็นข้อมูลเก่าเมื่อ refresh ไม่สำเร็จ แต่ไม่แสดงว่าสำเร็จ

ตรวจผล / แก้ปัญหา: revision เปลี่ยนจาก 1 เป็น 2 จาก remote จริง และ denied path ไม่ล้างค่าก่อนหน้าเป็นสถานะที่แต่งขึ้น

เก็บภาพที่ 3: Revision 2 พร้อม feedback ว่า denied-path test failed และแสดงผลก่อนหน้า

4. ตรวจ boundary และเตรียมดูแล 15 นาที

  1. สลับ Fake แล้ว Live ตรวจว่าป้าย source ตรงกับข้อมูล อย่าใช้ fake เป็นหลักฐานแทน cloud
  2. ใน service ลอง documentID ที่ไม่อยู่ใน allowlist แล้วดูว่า client ปฏิเสธ URL โดยไม่ส่งคำขอ จากนั้นคืนค่าเดิม
  3. ตรวจว่าภาพและ source ไม่มี token หรือ service-account key และแอปไม่มี client-write code
  4. เปิดหน้า usage ของ project เพื่อดูการอ่านจากการทดสอบ ไม่ตั้ง polling loop หลังจบการตรวจของผู้สอนให้ลบเฉพาะข้อมูลฝึกตามนโยบายของคุณ

ตรวจผล / แก้ปัญหา: แยก fake, validation failure และ backend denial ได้ และอ่าน cloud ได้อีกครั้งหลังกลับค่าถูก

เก็บภาพที่ 4: ผล Live accepted รอบสุดท้ายที่ยืนยันการกู้คืน

เพิ่มเติม (ไม่บังคับ) · 5 นาที

ออกแบบกฎสำหรับข้อมูลส่วนตัวแบบ user-scoped บนกระดาษ แล้วระบุ positive/negative tests โดยไม่เปิดใช้กับข้อมูลจริงในแล็บนี้ ไม่ต้องส่งภาพเพิ่ม

ยินดีด้วย!

คุณเชื่อม cloud จริงผ่าน REST และตรวจทั้ง remote change กับการปฏิเสธสิทธิ์ โดยใช้ fake แยกทดสอบ UI ได้
