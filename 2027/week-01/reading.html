02 / Framework evolution 26 / 32

2008 · Native smartphone SDKs

  • Problem: Developers needed a supported way to build native touchscreen apps and access iPhone capabilities.
  • Release: Apple announced the iPhone SDK in 2008, including UIKit for native interfaces.
  • UIKit supplied reusable views, controls and touch handling, reducing the UI work each app had to build itself.
  • Platform APIs exposed device services through supported interfaces and helped apps follow familiar interaction patterns.

Pair discussion: what did developers gain from a platform SDK, and what work remained?

Read further: Apple · iPhone SDK announcement (2008)

02 / Framework evolution 27 / 32

2011 · PhoneGap to Apache Cordova

  • Problem: Web developers faced unfamiliar native toolchains and repeated UI work when targeting multiple mobile platforms.
  • Milestone: PhoneGap brought web technology into mobile apps; its 2011 donation to Apache led to Cordova.
  • A packaged WebView reused HTML, CSS and JavaScript for the interface, carrying existing web skills into app development.
  • Plugins connected web code to native device features, reducing the need to implement every integration from scratch.

Check: why is a packaged hybrid app different from simply opening a website?

Read further: Apache Cordova · PhoneGap history · Cordova architecture

02 / Framework evolution 28 / 32

2014–2015 · Swift changes the language

  • Problem: Developers needed to express app logic more concisely while catching common mistakes earlier.
  • Release: Apple introduced the Swift language in 2014 and released it as open source in 2015.
  • Concise syntax and type inference reduced repetitive declarations while retaining type checking.
  • Safety features such as optionals made missing values explicit, helping developers handle them deliberately.

Classify Swift, UIKit and Xcode: language, framework or tool?

Read further: Apple · Swift becomes open source (2015)

02 / Framework evolution 29 / 32

2015–2018 · Sharing code across platforms

  • Problem: Separate iOS and Android implementations duplicated UI work and made shared features harder to maintain.
  • Releases: React Native became public in 2015; Flutter reached its first stable release, version 1.0, in 2018.
  • React Native reused React and JavaScript to describe interfaces backed by native components across platforms.
  • Flutter used Dart and a shared widget/rendering approach to reuse UI code across platforms.

Discuss: shared source code reduces which work? Why must we still test each platform?

Read further: React Native announcement (2015) · Google · Flutter 1.0 (2018)

02 / Framework evolution 30 / 32

2019 · SwiftUI brings declarative UI

  • Problem: As app state changed, manually updating UI elements made it easy for the screen and data to drift apart.
  • Release: Apple introduced SwiftUI in 2019 as a declarative UI framework for Apple platforms.
  • Developers described the interface for the current state instead of issuing each individual UI update.
  • SwiftUI coordinated updates as state changed, reducing manual synchronization between data and visible views.

Predict: when the count changes from 2 to 3, what should a label showing count display?

02 / Framework evolution 32 / 32

A brief history, with overlapping approaches

  • 2008: native SDKs made platform UI and device services reusable.
  • 2011: PhoneGap’s move to Apache marks a milestone in hybrid development.
  • 2014–2018: Swift, React Native and Flutter addressed different language and reuse goals.
  • 2019: SwiftUI introduced a declarative UI approach for Apple platforms.

Exit ticket: name one milestone, explain the problem it addressed, and connect one mobile characteristic to a framework need. These approaches overlap; this is not a replacement ladder.
