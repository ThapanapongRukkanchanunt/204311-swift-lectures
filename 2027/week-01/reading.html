What is a mobile framework?

  • A framework provides reusable structures and services for building an app.
  • The app supplies its screens and behavior; the framework coordinates recurring work.
  • Our history question: what development problem did each new approach try to solve?

Before modern smartphones: different constraints

  • Physical keys and small screens shaped earlier mobile interfaces.
  • Touchscreens brought direct gestures and more flexible layouts.
  • Richer apps increased the work of coordinating interface behavior and device capabilities.

02 / Framework evolution 26 / 32

2008 · Native smartphone SDKs

  • Apple announced the iPhone SDK in 2008, opening native app development to third-party developers.
  • UIKit supplied interface building blocks within the Apple platform.
  • Platform frameworks offered access to device capabilities and familiar interface behavior.
  • Building for another platform still required its own tools, APIs and adaptations.

Pair discussion: what did developers gain from a platform SDK, and what work remained?

Read further: Apple · iPhone SDK announcement (2008)

02 / Framework evolution 27 / 32

2011 · PhoneGap to Apache Cordova

  • Hybrid apps reused HTML, CSS and JavaScript skills inside a packaged mobile app.
  • A WebView displayed the web interface; plugins connected it to native device features.
  • After Adobe acquired Nitobi in 2011, PhoneGap code was donated to Apache and became Cordova.
  • Code reuse helped teams, but platform differences and plugin support still mattered.

Check: why is a packaged hybrid app different from simply opening a website?

Read further: Apache Cordova · PhoneGap history · Cordova architecture

02 / Framework evolution 28 / 32

2014–2015 · Swift changes the language

  • Apple introduced Swift in 2014 and released it as open source in 2015.
  • Swift is a programming language: it expresses data, logic and behavior.
  • UIKit and SwiftUI are UI frameworks; Xcode is a development environment.
  • A new language does not automatically replace an existing UI framework.

Classify Swift, UIKit and Xcode: language, framework or tool?

Read further: Apple · Swift becomes open source (2015)

02 / Framework evolution 29 / 32

2015–2018 · Sharing code across platforms

  • React Native was publicly released in 2015, using React to describe interfaces backed by native components.
  • Flutter reached version 1.0 in 2018, using Dart and its own widget/rendering approach.
  • Both aimed to reuse substantial app code across platforms through different architectures.
  • Platform integration, accessibility, testing and maintenance still needed attention.

Discuss: shared source code reduces which work? Why must we still test each platform?

Read further: React Native announcement (2015) · Google · Flutter 1.0 (2018)

02 / Framework evolution 30 / 32

2019 · SwiftUI brings declarative UI

  • Apple introduced SwiftUI in 2019 as a declarative framework for Apple-platform interfaces.
  • Describe the interface for the current state; the framework coordinates updates.
  • Contrast: manually change a label after an event versus describe a label from state.
  • Framework evolution changes how developers express UI behavior, not only how many platforms they target.

Predict: when the count changes from 2 to 3, what should a label showing count display?

02 / Framework evolution 32 / 32

A brief history, with overlapping approaches

  • 2008: native SDKs made platform UI and device services reusable.
  • 2011: PhoneGap’s move to Apache marks a milestone in hybrid development.
  • 2014–2018: Swift, React Native and Flutter addressed different language and reuse goals.
  • 2019: SwiftUI introduced a declarative UI approach for Apple platforms.

Exit ticket: name one milestone, explain the problem it addressed, and connect one mobile characteristic to a framework need. These approaches overlap; this is not a replacement ladder.
