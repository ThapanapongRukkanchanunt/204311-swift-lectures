ก่อนเริ่มต้น

[ลิงก์ Edpuzzle — ผู้สอนเพิ่มภายหลัง]

ใช้ defect ที่ทำซ้ำได้เพื่อเขียน test ซ่อมกฎ และตรวจว่าปุ่มเรียก model เดียวกัน โดยแยกผล automated test จาก manual check

[ภาพตัวอย่างแอป — ผู้สอนเพิ่มภายหลัง]

  1. Xcode ที่รองรับ Swift Testing (เช่น Xcode 16+/Swift 6+) หรือ Swift Playgrounds บน iPad สำหรับ harness ที่ให้มา
  2. ใช้ starter สำเนาใหม่ที่มีข้อผิดพลาด <= โดยตั้งใจ เก็บไฟล์ก่อนแก้ไว้แยก
  3. บน Mac เตรียม unit-test target; บน iPad ใช้ปุ่ม Run boundary checks ไม่ต้องติดตั้ง test framework ที่ไม่มีในเครื่อง

เตรียมโปรเจกต์

ดาวน์โหลด catch-up starter Week 14 แล้วแตกไฟล์ สร้างโปรเจกต์ SwiftUI App ใหม่ใน Xcode หรือ App ใหม่ใน Swift Playgrounds เก็บ App entry เดิมไว้ เพิ่มไฟล์ Swift ตาม README และแทนเฉพาะ ContentView.swift ของโปรเจกต์ใหม่ Run ให้ผ่านก่อนแก้ตามภารกิจ ไม่ทับโปรเจกต์เดิม Run boundary checks ต้องเห็น FAIL ก่อนซ่อมตามโจทย์

ภารกิจ

1. ทำซ้ำข้อผิดพลาดและเก็บหลักฐาน 15 นาที

  1. Run แอปแล้วกด Join สี่ครั้ง สังเกตว่าจำนวนเป็น 4 ทั้งที่ limit เป็น 3
  2. กด Run boundary checks เพื่อให้เห็น FAIL ที่เกิดจาก instance ทดสอบแยก
  3. อ่าน Capacity.join แล้วเขียนใน working notes ว่า count ต้องอยู่ระหว่าง 0 กับ 3 และ join เมื่อเต็มต้องคืน false ไม่ต้องส่ง notes เพิ่ม

ตรวจผล / แก้ปัญหา: ทั้ง UI และ harness เปิดเผยข้อผิดพลาดเดียวกัน หากเริ่มเห็น PASS ตรวจว่าใช้ starter ที่มี <=

เก็บภาพที่ 1: จำนวน 4 พร้อมผล FAIL ก่อนซ่อม

2. เพิ่มกรณีทดสอบให้ตรง requirement 20 นาที

  1. Mac: เพิ่ม Swift Testing file ใน unit-test target ใช้ @testable import ชื่อ app module จริง และ @Test ตาม excerpt; ให้ Capacity.swift อยู่ใน app target
  2. iPad: เพิ่ม case เข้า action Run boundary checks โดยสร้าง Capacity ใหม่ต่อ case ตรวจ leave ที่ 0 และ join เมื่อเต็ม ใช้ Bool รวมผลและแสดงชื่อ case ที่ผิด
  3. เพิ่มกรณี join หลัง leave หนึ่งครั้ง ต้องรับได้และกลับเป็น 3
  4. รันก่อนแก้ implementation ต้องยังพบ failure ที่ขอบเขต

CapacityTests.swift — Xcode unit-test target หลัง import Testing และ @testable import ของ app

@Test func rejectsFourthJoin() {
    var queue = Capacity()
    for _ in 0..<3 { #expect(queue.join()) }
    #expect(!queue.join())
    #expect(queue.count == 3)
}

ตรวจผล / แก้ปัญหา: test จับการคืนค่าและ count ไม่ใช่เพียง count > 0 หาก Mac หา module ไม่พบตรวจ Product Module Name และ target membership

เก็บภาพที่ 2: ผล test/harness ที่ระบุกรณีขอบเขตล้มเหลว

3. ซ่อมขั้นต่ำและเก็บ regression 20 นาที

  1. แก้ guard count <= limit เป็น guard count < limit ใน Capacity.join
  2. รัน test ชุดเดิมทั้งหมดโดยไม่เปลี่ยน expected values
  3. ตรวจกรณี 0, 1, 2, 3 และ join ซ้ำเมื่อเต็ม ค่าต้องคง 3
  4. เก็บ test ไว้หลังซ่อม อย่าลบ case ที่เคยแดง

ตรวจผล / แก้ปัญหา: ทุก case ที่ออกแบบผ่าน หากยังแดงอ่าน actual/expected และตรวจว่า test ใช้ไฟล์ model ที่แก้จริง

เก็บภาพที่ 3: ผล tests ผ่านหรือ harness PASS หลังซ่อม

4. ตรวจ UI wiring และ accessibility 20 นาที

  1. Run ใหม่แล้วกด Join สี่ครั้ง จำนวนบน UI ต้องไม่เกิน 3 และ Leave ไม่ต่ำกว่า 0
  2. Mac ถ้ามี UI-test target: ใช้ accessibilityIdentifier joinQueue และ queueCount ตาม starter ตรวจ tap หนึ่งครั้งแล้ว label เป็น 1 จาก launch ใหม่; หากไม่พร้อมให้ทำ manual sequence เดียวกันและระบุว่าไม่ได้รัน UI automation
  3. iPad: ทำ sequence ด้วยมือ ตรวจ large text และ VoiceOver ว่าปุ่มมีชื่อและจำนวนอ่านได้
  4. ลองเปลี่ยน implementation กลับเป็น <= ในสำเนาชั่วคราวเพื่อยืนยัน regression จับได้ แล้วคืน < และรันผ่านก่อนเก็บงาน

ตรวจผล / แก้ปัญหา: UI ใช้กฎที่ซ่อมแล้วและชื่อ control อ่านเข้าใจได้ ไม่อ้างว่าผ่าน XCTest หากตรวจด้วยมือ

เก็บภาพที่ 4: UI หลัง join เกินความจุแล้วยังคง 3 พร้อมผล harness PASS
